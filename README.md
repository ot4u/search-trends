# Search Trends

Сервис на Go для аналитики поисковых запросов в реальном времени.

**Суть:** читает события из NATS JetStream, держит в памяти окно популярности за 5 минут, отдаёт Top-N по HTTP.

**Как устроен внутри:**

- одна горутина пишет (без мьютексов);
- кольцевое окно: 300 бакетов по 1 секунде;
- кэш снимков Top-N, обновление раз в секунду;
- стоп-лист, нормализация запросов, упрощённая защита от накрутки.

## HTTP API

- `GET /api/v1/trending?limit=N` — Top-N популярных запросов
- `GET /api/v1/stoplist` — текущий стоп-лист
- `POST /api/v1/stoplist` — добавить слово (`{"word": "spam"}`)
- `DELETE /api/v1/stoplist/{word}` — удалить слово
- `GET /healthz` — проверка живости
- `GET /metrics` — метрики Prometheus
- `GET /debug/pprof/*` — профилирование

Пример ответа trending:

```json
{
  "generated_at": "2026-05-24T12:00:01Z",
  "window_seconds": 300,
  "limit": 10,
  "items": [
    {"query": "iphone 16", "score": 1230, "rank": 1}
  ]
}
```

Подробнее — [docs/architecture.md](docs/architecture.md).

## Событие в NATS

Тема по умолчанию: `search.events`. Тело сообщения — JSON:

```json
{
  "request_id": "8f4d6c4d-0d12-4d55-9f9d-1f1d6f8b7a11",
  "query": "купить айфон 17",
  "timestamp": "2026-05-24T12:00:01Z"
}
```

- **request_id** — идентификатор для логов и разбора, почему событие не дошло или не подтвердилось;
- **query** — текст поиска; дальше нормализуется, проверяется по стоп-листу, участвует в антифроде;
- **timestamp** — время на стороне отправителя; по нему событие попадает в нужную секунду окна (с допустимым сдвигом по часам).

Подтверждение в брокере — только после того, как писатель реально принял событие в окно.

## Зачем такая архитектура

Статистика живёт пять минут, запросов к топу обычно **гораздо больше**, чем новых событий. Поэтому:

- **всё в памяти, без базы** — иначе лишняя задержка ради данных, которые всё равно быстро устаревают;
- **один писатель** — consumer только ставит события в очередь, окно редактирует одна горутина, без блокировок на горячем пути;
- **кольцевое окно и общий счётчик** — быстрое добавление и построение топа без обхода трёхсот секундных ячеек;
- **snapchots топа раз в секунду** — ответ по сети чаще всего чтение готового результата, а не пересчёт на каждый запрос;
- **стоп-лист через копию карты** — проверка слова не тормозит приём событий;
- **JetStream в NATS** — простой локальный запуск, достаточно для одного потребителя.

Поток: брокер → ограниченная очередь → write горутина → окно → кэш снимков → ответ клиенту.

## Компромиссы

1. **Память может раздуваться от уникальных запросов**  
   Решение: лимит `MAX_UNIQUE_QUERIES`.  
   Цена: редкие запросы под нагрузкой отбрасываются.

2. **Очень много чтений топа**  
   Решение: кэш снимков, обновление раз в секунду.  
   Цена: в ответе топ может отставать примерно на секунду.

3. **Параллельная запись в одно окно**  
   Решение: один писатель на всё состояние.  
   Цена: при экстремальной записи узкое место — одна горутина.

4. **Нужно убрать слово из топа**  
   Решение: стоп-лист действует только на новые события.  
   Цена: старые слова в окне уйдут сами за пять минут.

5. **Один запрос в разных формулировках**  
   Решение: лёгкая нормализация текста.  
   Цена: иногда разные запросы склеиваются в один.

6. **Накрутка популярности**  
   Решение: при частых повторах вес падает с десяти до одного, без полного отбрасывания.  
   Цена: защита приблизительная, сложную атаку не закроет.

## Производительность

Окружение прогонов: **macOS, Apple M3**, стек в Docker (`make docker-up`).

**бенчмарки** (`make bench`):

- добавление в окно — ~190 нс на операцию;
- чтение готового снимка — ~5 нс (без аллокаций);
- пересчёт Top-100 по 100k ключам — ~0,62 мс (в фоне, раз в секунду).

**Нагрузочные тесты** (vegeta, `make load-test`):

- чтение 10k запросов/с — 100% успех, p99 **2,6 мс** (`limit=10`);
- ротация limit 5–100 — 100% успех, p99 **126 мс** (крупные ответы, редкие выбросы);
- смешанный режим 5k чтений/с + 1k записей в NATS — 100% успех, p99 **11,7 мс**.

Детали и выводы — [docs/benchmarks.md](docs/benchmarks.md), [docs/load_testing.md](docs/load_testing.md).
