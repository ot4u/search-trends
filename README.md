# Search Trends

`search-trends` — сервис на Go, который получает поисковые события из NATS JetStream, поддерживает в памяти окно популярности запросов за последние 5 минут и отдает Top-N популярных запросов по HTTP.

Основной фокус реализации:

- высокая скорость обработки,
- предсказуемое потребление памяти,
- минимальные задержки чтения,
- простая и прозрачная архитектура.

## Архитектура

### Общая схема

```text
NATS JetStream
    ->
bounded channel
    ->
single writer goroutine
    ->
sliding window
    ->
snapshot cache
    ->
HTTP API
```

---

### Контракт данных

Сервис получает поисковые события из NATS JetStream в формате JSON.

Пример payload:

```json
{
  "request_id": "8f4d6c4d-0d12-4d55-9f9d-1f1d6f8b7a11",
  "query": "купить айфон 17",
  "timestamp": "2026-05-24T12:00:01Z"
}
```
---

#### Описание полей

**request_id** - Используется для:
- трассировки запросов,
- упрощения отладки,
- поиска проблем в обработке событий.

Без request_id значительно сложнее анализировать потерянные или задержанные события.

**query** - основное поле системы, которое:
- нормализуется,
- проверяется через stop-list,
- участвует в anti-fraud,
- попадает в sliding window,
- участвует в вычислении Top-N.

**timestamp** - Использование producer timestamp позволяет корректно размещать событие внутри временного окна.


### Почему выбрана single-writer модель?

Все изменения состояния выполняются только одной горутиной.

Consumer из NATS не изменяет данные напрямую. Он только:

- читает сообщения,
- декодирует их,
- помещает в очередь.

Единственным владельцем состояния является writer goroutine.

Почему это сделано:

- нет конкуренции за общее состояние,
- не требуется большое количество мьютексов,
- проще обеспечить корректное истечение окна,
- поведение системы остается предсказуемым под нагрузкой.

Компромисс:

Один writer теоретически может стать ограничением при экстремальной нагрузке.

Для текущего масштаба задачи это считается оправданным упрощением.

---

### Sliding Window

Для хранения статистики используется кольцевой буфер:

- 300 бакетов,
- 1 бакет = 1 секунда,
- общее окно = 5 минут.

Каждый бакет хранит:

```text
map[string]uint64
```

где:

- ключ — нормализованный поисковый запрос,
- значение — количество запросов за секунду.

---

### Почему выбрана именно такая структура

Кольцевой буфер позволяет:

- добавлять события за O(1),
- дешево удалять устаревшие данные,
- переиспользовать память,
- не выполнять полную очистку окна.

При сдвиге окна:

- старый бакет очищается,
- его значения вычитаются из глобального счетчика,
- бакет переиспользуется повторно.

Такой подход хорошо подходит для потоковой обработки realtime-событий.

---

### Global Counter

Дополнительно используется:

```text
map[string]uint64
```

который хранит уже агрегированную статистику за текущее окно.

Пример:

```text
bucket[q] += weight
globalCounter[q] += weight
```

При удалении устаревшего бакета:

```text
globalCounter[q] -= expiredBucket[q]
```

Если значение становится нулевым — ключ удаляется.

---

### Почему нужен global counter

Без него при каждом запросе Top-N пришлось бы:

- обходить все 300 бакетов,
- заново агрегировать статистику.

Это дорого при большом количестве чтений.

Global counter позволяет:

- держать уже готовую агрегированную статистику,
- вычислять Top-N значительно дешевле,
- сделать стоимость чтения независимой от размера окна.

---

### Вычисление Top-N

Для Top-N используется min-heap фиксированного размера.

Полная сортировка всех запросов имела бы сложность:

```text
O(M log M)
```

где:

- M — количество уникальных запросов.

Использование heap снижает сложность до:

```text
O(M log N)
```

где:

- N — размер Top.

Это особенно важно при большом количестве уникальных запросов.

---

### Snapshot Cache

Сервис предполагает нагрузку, где чтений значительно больше, чем записей.

Чтобы не пересчитывать Top-N на каждый HTTP-запрос:

- snapshots пересчитываются в фоне раз в секунду,
- HTTP API отдает уже готовые результаты.

Предвычисляются:

- top-5
- top-10
- top-25
- top-50
- top-100

Snapshots публикуются через atomic swap.

---

### Почему это сделано

Такой подход:

- стабилизирует задержки API,
- уменьшает нагрузку на CPU,
- делает чтения практически постоянными по стоимости.

Компромисс:

API может отставать от актуального состояния примерно на одну секунду.

Для сервиса трендов это считается допустимым.

---

### Stop-list

Stop-list поддерживается динамически.

Хранение:

```text
map[string]struct{}
```

Обновление:

- copy-on-write,
- публикация через atomic swap.

---

### Почему выбрана именно такая структура

Преимущества:

- проверка выполняется за O(1),
- минимальное потребление памяти,
- чтения не блокируются.

При обновлении:

- создается новая копия map,
- в нее вносятся изменения,
- затем выполняется атомарная замена.

Это позволяет не блокировать поток обработки событий.

---

### Поведение stop-list

Stop-list влияет только на новые события.

Уже существующие данные внутри окна не переиндексируются.

Почему так:

Полная переиндексация:

- дорогая по CPU,
- ухудшает задержки,
- усложняет конкурентный доступ.

Через 5 минут старые данные естественным образом исчезают из окна.

Компромисс:

После добавления stop-слова оно исчезает из Top-N не мгновенно.

---

### Нормализация запросов

Перед обработкой запрос нормализуется:

- перевод в нижний регистр,
- удаление лишних пробелов,
- удаление пунктуации,
- схлопывание повторяющихся пробелов,
- удаление intent-слов.

Пример:

```text
"Купить   Айфон-17!!!"
↓
"айфон 17"
```

---

### Почему используется lightweight-нормализация

Без нормализации один и тот же тренд мог бы распадаться на множество вариантов:

- купить айфон 17
- новый айфон 17
- заказать айфон 17
- айфон 17

Это ухудшает качество Top-N.

Полноценный NLP-анализ:

- слишком тяжелый для горячего пути,
- избыточен для задачи,
- усложняет систему.

Поэтому выбрана простая и дешевая нормализация.

Компромисс:

В сложных случаях нормализация может ошибаться и объединять не совсем одинаковые запросы.

---

### Anti-Fraud

Реализована упрощенная защита от накрутки.

Для текущей секунды ведутся счетчики запросов:

```text
map[string]uint64
```

Если частота превышает порог:

- запрос считается подозрительным,
- его вес уменьшается.

Используются веса:

- обычный запрос = 10,
- подозрительный запрос = 1.

---

### Почему не используется полный drop

Резкие всплески бывают и у реальных трендов.

Полное удаление могло бы:

- скрывать настоящие события,
- искажать статистику.

Уменьшение веса позволяет:

- снизить влияние накрутки,
- сохранить реакцию на реальные пики.

Компромисс:

Механизм остается приблизительным и не защищает от сложных распределенных атак.

---

### Ограничение памяти

Количество уникальных запросов ограничено параметром:

```text
MAX_UNIQUE_QUERIES
```

Если лимит достигнут:

- популярные запросы продолжают обновляться,
- новые редкие запросы могут игнорироваться.

---

### Почему это необходимо

Пользовательские запросы имеют неограниченную кардинальность.

Без ограничения злоумышленник может:

- генерировать случайные строки,
- провоцировать рост памяти,
- привести сервис к нехватке памяти.

---

### Почему выбран именно такой подход

Главная ценность сервиса — популярные запросы.

Потеря части редких запросов:

- почти не влияет на качество Top-N,
- но позволяет сохранить стабильность системы.

Компромисс:

Редкие запросы теряются под сильной нагрузкой.

---

## Почему не используется база данных

Все данные живут только последние 5 минут.

База данных:

- увеличила бы задержки,
- добавила бы сетевые вызовы,
- усложнила бы систему,
- не дала бы существенной пользы для задачи realtime-trending.

Поэтому состояние хранится только в памяти.

---

## Почему выбран NATS JetStream

JetStream:

- прост в локальном запуске,
- имеет небольшой операционный overhead,
- хорошо интегрируется с Go,
- поддерживает persistence и replay.

Kafka был бы оправдан при:

- большом количестве нижестоящих потребителей,
- сложной streaming-платформе,
- длительном хранении истории.

Для текущей задачи JetStream дает достаточную надежность при меньшей сложности.

---

## Почему выбран chi

Используется:

- net/http
- chi router

Причины:

- минимальный overhead,
- идиоматичный Go API,
- отсутствие тяжелой фреймворк абрстрации,
- хорошая производительность.

Для данной задачи полноценный framework не требуется.

---

## Проблемы постановки и принятые решения

### 1. Неограниченный рост памяти

Проблема:
пользовательские запросы могут быть бесконечно уникальными.

Решение:
ограничение MAX_UNIQUE_QUERIES.

Компромисс:
часть редких запросов может теряться.

---

### 2. Большое количество чтений

Проблема:
Top-N читается значительно чаще, чем обновляется.

Решение:
snapshot cache.

Компромисс:
данные могут отставать примерно на 1 секунду.

---

### 3. Конкурентное обновление окна

Проблема:
mutex-heavy архитектура ухудшила бы производительность.

Решение:
single-writer модель.

Компромисс:
одна goroutine может стать ограничением при экстремальной нагрузке.

---

### 4. Обновление stop-list

Проблема:
полная переиндексация окна слишком дорогая.

Решение:
stop-list влияет только на новые события.

Компромисс:
старые данные исчезают постепенно.

---

### 5. Повторяющиеся формы запросов

Проблема:
один тренд может существовать в нескольких формах.

Решение:
lightweight-нормализация.

Компромисс:
возможны ошибки объединения запросов.

---

### 6. Накрутка популярных запросов

Проблема:
искусственные всплески могут искажать Top-N.

Решение:
уменьшение веса подозрительных запросов.

Компромисс:
защита остается приблизительной.

## Monitoring

Минимальный стек без лишней сложности:

- **Prometheus** — сбор метрик, алерты, localhost:9090
- **Grafana** — один дашборд, localhost:3000
- **structured logs** — `slog` с `request_id`, latency, status, queue size

Запуск стека:

```bash
make docker-up
```

Почему именно так:

- достаточно для highload backend-сервиса с in-memory state,
- не требует Kubernetes, OpenTelemetry, Loki/Jaeger/Tempo,
- локально поднимается одной командой,
- метрики уже отражают критическую зону: ingest, snapshots, HTTP, NATS lag, memory.

Что помогает обнаруживать:

- рост latency на чтении (snapshot/HTTP),
- переполнение bounded queue,
- отставание snapshot cache,
- рост consumer lag,
- утечки/рост heap,
- всплески dropped/downweighted/stoplist событий.

Ключевые метрики:

| Метрика | Назначение |
| --- | --- |
| `search_trends_http_requests_total` | RPS и error rate |
| `search_trends_http_request_duration_seconds` | p50/p95/p99 latency |
| `search_trends_events_total` | ingest outcomes |
| `search_trends_events_dropped_total` | dropped (capacity/stale/future) |
| `search_trends_antifraud_downweighted_total` | anti-fraud downweight |
| `search_trends_ingest_queue_size` / `_capacity` | backpressure |
| `search_trends_unique_queries` | cardinality окна |
| `search_trends_memory_alloc_bytes` | heap |
| `search_trends_nats_consumer_lag_seconds` | ingest lag |
| `search_trends_snapshot_age_seconds` | свежесть cache |
| `search_trends_snapshot_refresh_duration_seconds` | стоимость refresh |

Dashboard: `prometheus/grafana.json` (provisioning через docker-compose).

## Alerts

Правила: `prometheus/alerts.yml`, подключены в `prometheus/prometheus.yml`.

| Alert | Условие | Что сигнализирует |
| --- | --- | --- |
| `IngestQueueHighUsage` | queue > 90% capacity | writer не успевает, риск backpressure |
| `SnapshotStale` | snapshot age > 5s | сломался tick/refresh |
| `HTTPP99LatencyHigh` | HTTP p99 > 200ms | деградация read path |
| `NATSConsumerLagHigh` | lag > 10s | отставание от потока событий |

Alertmanager намеренно не добавлен: для локальной разработки и демонстрации достаточно rules в Prometheus UI (`/alerts`). В production rules переносятся в существующий Alertmanager as-is.

## pprof

Endpoint: `/debug/pprof` (chi `middleware.Profiler()` + `net/http/pprof`).

Примеры:

```bash

go tool pprof http://localhost:8080/debug/pprof/heap

```

Зачем: CPU горячие точки (Top-N, snapshot refresh), рост кучи  (окно/global counter), утечки горутин (writer/consumer).

В проде ручку нужно закрыть сетевым ACL или reverse proxy. В сервисе он включен для локальной диагностики.

## Graceful Shutdown

Порядок остановки:

1. остановка HTTP server,
2. остановка NATS consumer,
3. дренирование очереди,
4. завершение writer goroutine.

Это уменьшает риск потери уже принятых событий.

## Масштабирование

Текущая реализация содержит один узел.

Следующий шаг масштабирования:
1. шардирование по hash(query),
2. несколько независимых узлов,
3. объединение shard-local Top-N.

Такой подход позволяет сохранить:
- in-memory модель,
- single-writer архитектуру,
- простоту обработки.
