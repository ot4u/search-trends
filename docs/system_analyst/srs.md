# SRS для сервиса Search Trends

Версия документа: 1.0  

## 1. Введение

### 1.1. Цель документа

Документ фиксирует требования к сервису `Search Trends`: назначение, функциональность, ограничения, внешние интерфейсы, данные наблюдаемости и проектные допущения. SRS предназначен для системных аналитиков, разработчиков, QA, DevOps/SRE и потребителей API как единая точка согласования поведения сервиса.

### 1.2. Область применения проекта

`Search Trends` - backend-сервис аналитики поисковых запросов в реальном времени. Сервис принимает события поиска из NATS JetStream, держит in-memory скользящее окно популярности, рассчитывает Top-N поисковых запросов и предоставляет результат через HTTP API.

В область проекта входят:

- прием поисковых событий из NATS JetStream;
- нормализация запросов, стоп-лист и базовая защита от накрутки;
- расчет Top-N за скользящее окно;
- HTTP API для чтения трендов и управления стоп-листом;
- Prometheus-метрики, Grafana-дашборд, pprof и expvar для диагностики;
- локальный запуск через Docker Compose.

Вне области текущей версии:

- пользовательский интерфейс аналитики;
- долговременное хранение истории трендов;
- кластерная агрегация между несколькими инстансами;
- аутентификация и авторизация HTTP/NATS на уровне приложения;
- полнофункциональная ML/NLP-нормализация и сложный антифрод.

## 2. Общее описание

### 2.1. Перспектива продукта (место в экосистеме)

`Search Trends` находится между источниками поисковых событий и потребителями аналитики:

- источники событий публикуют JSON-сообщения в NATS JetStream;
- сервис читает события pull-consumer'ом, обрабатывает их одной writer-горутиной и обновляет in-memory состояние;
- клиенты аналитики читают Top-N через HTTP API;
- операторы управляют стоп-листом и диагностируют состояние через HTTP endpoints;
- Prometheus собирает метрики с `/metrics`, Grafana визуализирует состояние сервиса.

Сервис не использует базу данных для трендов. Данные актуальны в пределах скользящего окна и теряются при остановке процесса, что соответствует назначению "тренды прямо сейчас".

### 2.2. Основные функции продукта

- Принимать события поиска из NATS JetStream.
- Валидировать JSON и преобразовывать сообщение в доменную структуру `SearchEvent`.
- Нормализовать текст запроса: нижний регистр, удаление пунктуации/символов, фильтрация intent-слов.
- Исключать новые события, содержащие слова из стоп-листа.
- Снижать вес частых повторов одного запроса в текущую секунду.
- Вести скользящее окно популярности за настраиваемый период.
- Пересчитывать и кэшировать снимки Top-N раз в секунду.
- Отдавать Top-N через `GET /api/v1/trending`.
- Управлять стоп-листом через HTTP API.
- Экспортировать метрики, health check и диагностические endpoints.

### 2.3. Характеристики пользователей (основной потребитель API)

| Роль | Цели | Канал взаимодействия |
| --- | --- | --- |
| Dashboard / аналитический клиент | Получать актуальный Top-N запросов с малой задержкой. | HTTP API `/api/v1/trending` |
| Источник поисковых событий | Передавать события поиска в поток обработки. | NATS JetStream `search.events` |
| Оператор / SRE | Следить за здоровьем, задержками, очередью, лагом consumer'а и состоянием снимков. | `/healthz`, `/metrics`, Grafana, pprof |
| Администратор контента / оператор | Добавлять и удалять слова стоп-листа. | HTTP API `/api/v1/stoplist` |
| Разработчик / QA | Проверять корректность алгоритмов, контрактов и производительности. | Unit tests, benchmarks, load tests, OpenAPI, AsyncAPI |

### 2.4. Ограничения и допущения

- Сервис работает как один инстанс приложения; горизонтальное шардирование описано как возможное развитие, но не реализовано.
- Состояние трендов хранится в памяти процесса и не переживает рестарт.
- Скользящее окно по умолчанию равно `300` секунд (`WINDOW_SECONDS`).
- HTTP API по умолчанию слушает `:8080`.
- NATS subject по умолчанию: `search.events`; stream: `search-events`; durable: `search-trends`.
- Writer-горутина является единственным компонентом, изменяющим окно, антифрод-счетчики и snapshot cache.
- HTTP-запросы Top-N читают готовые снимки и не пересчитывают Top-N синхронно.
- Максимальная кардинальность запросов ограничена `MAX_UNIQUE_QUERIES`, по умолчанию `200000`.
- Доступные snapshot limits задаются `SNAPSHOT_LIMITS`, по умолчанию `5,10,25,50,100`.
- Защита от накрутки является эвристической: после порога повторов в секунду вес события снижается, но событие не отбрасывается.
- HTTP API, pprof и управление стоп-листом не имеют встроенной авторизации; сетевой доступ должен ограничиваться инфраструктурой.

## 3. Специфические требования (Specific Requirements)

### 3.1. Функциональные требования

| ID | Описание | Приоритет |
| --- | --- | --- |
| FR-001 | Система должна читать сообщения из NATS JetStream subject `search.events` через pull consumer. | MUST |
| FR-002 | Система должна поддерживать настройки NATS через переменные окружения: URL, stream, subject, durable, batch, timeout, ack wait, max ack pending и auto-provision. | MUST |
| FR-003 | При `NATS_AUTO_PROVISION=true` система должна создавать JetStream stream с subject `search.events`, file storage, limits retention и `MaxAge=10m`, если stream отсутствует. | SHOULD |
| FR-004 | Система должна принимать JSON payload события с полями `request_id`, `query`, `timestamp`. | MUST |
| FR-005 | Система должна подтверждать и отбрасывать сообщения с невалидным JSON, фиксируя outcome `invalid_json`. | MUST |
| FR-006 | Система должна помещать валидные события во внутреннюю ограниченную очередь перед обработкой writer'ом. | MUST |
| FR-007 | Система должна обрабатывать события последовательно одной writer-горутиной, без прямой модификации окна из NATS consumer'а или HTTP handler'ов. | MUST |
| FR-008 | Система должна подтверждать JetStream-сообщение после принятия события writer'ом в окно. | MUST |
| FR-009 | Система должна нормализовать запрос: приводить к нижнему регистру, заменять пунктуацию/символы пробелами и удалять intent-слова `купить`, `заказать`, `новый`, `дешево`. | MUST |
| FR-010 | Система должна игнорировать события, чей запрос пуст после нормализации. | MUST |
| FR-011 | Система должна игнорировать новые события, содержащие хотя бы один токен из стоп-листа. | MUST |
| FR-012 | Система должна поддерживать добавление, удаление и получение отсортированного стоп-листа через HTTP API. | MUST |
| FR-013 | Система должна принимать в стоп-лист только одно нормализованное слово; пустые значения и несколько токенов должны возвращать ошибку 400. | MUST |
| FR-014 | Система должна снижать вес частых повторов одного нормализованного запроса в текущую секунду после порога `ANTIFRAUD_THRESHOLD_PER_SECOND`. | SHOULD |
| FR-015 | Система должна учитывать `timestamp` события; отсутствующее или zero time значение заменяется текущим UTC-временем обработки. | MUST |
| FR-016 | Система должна игнорировать слишком старые события и события дальше допустимого future skew (`MAX_FUTURE_SKEW`). | MUST |
| FR-017 | Система должна ограничивать число уникальных запросов в окне через `MAX_UNIQUE_QUERIES` и игнорировать новые уникальные запросы при достижении лимита. | SHOULD |
| FR-018 | Система должна вести кольцевое скользящее окно с односекундными bucket'ами и общим счетчиком по окну. | MUST |
| FR-019 | Система должна пересчитывать snapshot cache Top-N раз в секунду для настроенных `SNAPSHOT_LIMITS`. | MUST |
| FR-020 | Система должна возвращать Top-N через `GET /api/v1/trending`, параметр `limit` по умолчанию равен `10`. | MUST |
| FR-021 | Система должна возвращать 400 для нечислового, неположительного или превышающего максимальный snapshot limit значения `limit`. | MUST |
| FR-022 | Система должна возвращать 503, если снимки Top-N временно недоступны. | MUST |
| FR-023 | Система должна предоставлять `/healthz` для проверки живости приложения. | MUST |
| FR-024 | Система должна предоставлять `/metrics` в Prometheus text exposition format. | MUST |
| FR-025 | Система должна предоставлять pprof и expvar endpoints для диагностики в локальном/внутреннем окружении. | SHOULD |
| FR-026 | Система должна писать структурированные HTTP-логи с request id, методом, маршрутом, статусом, задержкой и размером очереди. | SHOULD |
| FR-027 | Система должна корректно завершаться: остановить HTTP, остановить consumer, закрыть вход очереди и дождаться writer'а. | MUST |

### 3.2. Нефункциональные требования

#### Производительность

| ID | Требование | Приоритет |
| --- | --- | --- |
| NFR-PERF-001 | Чтение Top-N должно выполняться из snapshot cache, без пересчета Top-N на каждый HTTP-запрос. | MUST |
| NFR-PERF-002 | Система должна выдерживать сценарий чтения `GET /api/v1/trending?limit=10` на уровне 10 000 RPS в локальном Docker Compose окружении с 100% успешных 2xx ответов по результатам нагрузочного теста. | SHOULD |
| NFR-PERF-003 | Для сценария 10 000 RPS чтения `limit=10` ориентир p99 задержки составляет около 2.6 мс на macOS Apple M3; значения на другом железе должны сравниваться относительно локального baseline. | SHOULD |
| NFR-PERF-004 | Смешанный сценарий 5 000 RPS чтения и 1 000 событий/с записи в NATS должен оставаться без HTTP-ошибок в локальном нагрузочном тесте. | SHOULD |
| NFR-PERF-005 | Пересчет Top-N должен выполняться фоново примерно раз в секунду; возраст snapshot должен контролироваться метрикой и алертом. | MUST |

#### Надежность

| ID | Требование | Приоритет |
| --- | --- | --- |
| NFR-REL-001 | Очередь ingest должна быть ограниченной по размеру, чтобы контролировать давление на память. | MUST |
| NFR-REL-002 | JetStream consumer должен использовать explicit/manual ack, чтобы не подтверждать событие до обработки writer'ом. | MUST |
| NFR-REL-003 | HTTP router должен восстанавливаться после panic через middleware recoverer. | SHOULD |
| NFR-REL-004 | Сервис должен экспортировать метрики очереди, возраста snapshot, lag consumer'а и ошибок обработки для раннего обнаружения деградации. | MUST |
| NFR-REL-005 | Сервис должен поддерживать graceful shutdown с ожиданием writer'а после закрытия входа очереди. | MUST |

#### Безопасность

| ID | Требование | Приоритет |
| --- | --- | --- |
| NFR-SEC-001 | Встроенная авторизация HTTP API отсутствует; в продуктивном окружении доступ к API управления стоп-листом, `/metrics`, `/debug/*` должен ограничиваться сетевыми правилами, reverse proxy или инфраструктурной авторизацией. | MUST |
| NFR-SEC-002 | pprof и expvar endpoints не должны быть доступны из публичной сети. | MUST |
| NFR-SEC-003 | Сервис должен валидировать входные JSON-тела и параметры HTTP-запросов, возвращая 400 для некорректного пользовательского ввода. | MUST |
| NFR-SEC-004 | TLS, NATS credentials и секреты не реализуются в коде приложения и должны настраиваться на уровне окружения/инфраструктуры при необходимости. | SHOULD |

### 3.3. Требования к внешним интерфейсам

| Интерфейс | Назначение | Контракт / описание |
| --- | --- | --- |
| HTTP API | Top-N, стоп-лист, health, metrics, diagnostics. | [OpenAPI 3.1](openapi.yaml) |
| NATS JetStream | Входящие события поиска. | [AsyncAPI 2.6](asyncapi.yaml) |
| Prometheus scrape | Сбор метрик приложения. | `GET /metrics`, также описан в [monitoring.md](../developer/monitoring.md) |
| Grafana | Просмотр RPS, latency, queue, lag, snapshot age и памяти. | [prometheus/grafana.json](../../prometheus/grafana.json) |
| pprof / expvar | Диагностика CPU, heap, goroutine, runtime trace и expvar. | `/debug/pprof/*`, `/debug/vars` |

HTTP API должен соответствовать OpenAPI-спецификации:

- `GET /api/v1/trending?limit=N`;
- `GET /api/v1/stoplist`;
- `POST /api/v1/stoplist`;
- `DELETE /api/v1/stoplist/{word}`;
- `GET /healthz`;
- `GET /metrics`;
- `/debug/pprof/*`, `/debug/vars`.

NATS payload должен соответствовать AsyncAPI-спецификации:

```json
{
  "request_id": "8f4d6c4d-0d12-4d55-9f9d-1f1d6f8b7a11",
  "query": "купить айфон 17",
  "timestamp": "2026-05-24T12:00:01Z"
}
```

### 3.4. Требования к данным

#### Основные доменные данные

| Данные | Требование |
| --- | --- |
| `request_id` | Используется для логов и диагностики; в коде не валидируется как UUID. |
| `query` | Сырые данные поискового запроса; после нормализации становятся ключом окна. |
| `timestamp` | UTC-время события; определяет bucket окна с учетом ограничений stale/future. |
| `score` | Накопленный вес нормализованного запроса в текущем окне. |
| `rank` | Позиция запроса в Top-N. |
| `generated_at` | UTC-время генерации snapshot. |
| `window_seconds` | Размер скользящего окна в секундах. |

#### Алерты

| Алерт | Условие | Назначение |
| --- | --- | --- |
| `IngestQueueHighUsage` | Очередь заполнена более чем на 90% в течение 1 минуты. | Writer не успевает за ingest. |
| `SnapshotStale` | `search_trends_snapshot_age_seconds > 5` в течение 1 минуты. | Snapshot cache не обновляется. |
| `HTTPP99LatencyHigh` | HTTP p99 выше 200 мс в течение 2 минут. | Деградация пользовательской задержки API. |
| `NATSConsumerLagHigh` | Lag consumer'а выше 10 секунд в течение 1 минуты. | Обработка отстает от входящего потока. |

### 4.2. Допущения по проектированию (Trade-offs, которые описаны в README)

| Решение | Причина | Цена / ограничение |
| --- | --- | --- |
| Хранить тренды в памяти без базы данных | Данные живут несколько минут, нужна низкая задержка. | Состояние теряется при рестарте, нет исторической аналитики. |
