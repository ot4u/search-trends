# Нагрузочное тестирование

Проверяем сервис под нагрузкой, при необходимости одновременная запись в NATS. Инструмент — [vegeta](https://github.com/tsenart/vegeta), скрипты в `tests/load/`.

---

## Что нужно перед запуском

- установлен `vegeta` (через `go install` или пакет системы);
- поднят стек: `make docker-up`;
- доступны `http://localhost:8080` и `nats://localhost:4222`.

Скрипты сами заливают события в JetStream через `tests/load/publisher`, ждут появления данных в trending и только потом гоняют vegeta. Отдельно кэш Go в репозитории не создаётся.

---

## Запуск

Все три сценария подряд:

```bash
make load-test
```

Один сценарий:

```bash
bash tests/load/read-10k.sh
bash tests/load/cache-hit.sh
bash tests/load/mixed.sh
```

Параметры через переменные окружения, например:

```bash
RATE=5000 DURATION=60s bash tests/load/read-10k.sh
```

Отчёт vegeta идёт в терминал, файлы в репозитории не пишутся.

---

## Сценарии

### 1. Упор на чтение (`read-10k.sh`)

- перед тестом — 50 000 событий в NATS (`SEED_EVENTS`);
- нагрузка: 10 000 запросов/с, 30 с;
- цель: `GET /api/v1/trending?limit=10`.

Проверяем, что при почти только чтениях ответы идут из кэша снимков, а не с пересчётом Top-N на каждый запрос.

### 2. Разные размеры Top-N (`cache-hit.sh`)

- те же 50 000 событий и 10 000 запросов/с;
- цели чередуются: limit 5, 10, 25, 50, 100 (`cache-hit.targets`).

Проверяем, что все предвычисленные лимиты из `SNAPSHOT_LIMITS` отдаются с приемлемой задержкой.

### 3. Чтение и запись (`mixed.sh`)

- прогрев: 20 000 событий;
- vegeta: 5 000 запросов/с к trending;
- параллельно publisher: 1 000 событий/с в NATS, 30 с.

Проверяем, что HTTP не «сыпется», пока идёт фоновая запись.

## Выводы

1. **Чтение на 10k RPS держится уверенно.** Медиана около полумиллисекунды, p99 около 2,6 мс — для отдачи готового снимка это ожидаемо хороший результат.

2. **Кэш снимков работает как задумано.** Основной сценарий чтения не упирается в пересчёт Top-N на запрос; иначе при таком RPS задержки были бы на порядки выше (см. бенчмарк `BuildTopN` в [benchmarks.md](benchmarks.md)).

3. **Сценарий с разными limit тяжелее по хвосту.** p99 ~126 мс связан с большим телом ответа (до top-100) и разбросом нагрузки по разным эндпоинтам, а не с отказами — ошибок не было.

4. **Смешанная нагрузка остаётся стабильной.** При 5k чтений/с и 1k записей/с в NATS все запросы успешны; p99 ~12 мс показывает, что writer и очередь справляются, хотя хвост выше, чем при чистом чтении.

5. **Для сравнения прогонов** фиксируйте версию Go, железо и переменные `RATE` / `SEED_EVENTS`. На другой машине цифры будут другими, порядок величин обычно сохраняется.

Во время прогона имеет смысл смотреть в Grafana: размер очереди (`search_trends_ingest_queue_size`), возраст снимка, лаг consumer — см. [monitoring.md](monitoring.md).

---

## Как читать отчёт vegeta

- **Success** — доля ответов 2xx; должна быть близка к 100%.
- **Latencies** — min, среднее, p50, p90, p95, p99, max.
- **Throughput** — фактические запросы в секунду.

Если много 503 или таймаутов — сервис не поднят или снимок ещё пуст (не дождались `wait_for_trending_data`). Если падает success при большом `limit` — проверьте, что limit ≤ 100 (максимум в `SNAPSHOT_LIMITS`).

## Утилита publisher

Для ручной заливки:

```bash
go run ./tests/load/publisher \
  --nats-url=nats://localhost:4222 \
  --subject=search.events \
  --count=50000
```

Или потоком:

```bash
go run ./tests/load/publisher \
  --rate=1000 --duration=30s
```

Формат сообщения — в [architecture.md](architecture.md#контракт-событий-nats).

---

## Ограничения

- один инстанс приложения в docker-compose, не кластер;
- не заменяют долгий прод-мониторинг под реальным трафиком;
- не сравнивают «с кэшем и без» автоматически — для этого нужен отдельный эксперимент или pprof.
