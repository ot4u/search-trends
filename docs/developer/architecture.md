# Архитектура

Как устроен `search-trends`, почему сделано именно так и какие компромиссы заложены в дизайн.

---

## Общая схема

```text
NATS JetStream (pull-подписчик)
        │
        ▼
  ограниченная очередь (QUEUE_SIZE, по умолчанию 65536)
        │
        ▼
  одна горутина-писатель
        │
        ├── скользящее окно (300 × 1 с)
        ├── антифрод (счётчики на текущую секунду)
        ├── стоп-лист (копия при записи)
        └── обновление снимков (раз в секунду)
                │
                ▼
        кэш снимков (atomic.Pointer)
                │
                ▼
        HTTP API (chi) — отдача готового Top-N
```

**Главное правило:** менять окно, счётчики антифрода и публиковать снимки может только горутина-писатель (`internal/usecase/ingest/service.go`). Подписчик NATS и HTTP-обработчики состояние не трогают.

---

## Слои в репозитории

- **`internal/domain/trending`** — кольцевое окно, Top-N на куче, нормализация запросов
- **`internal/domain/stoplist`** — стоп-лист, обновление через копию карты
- **`internal/domain/antifraud`** — веса событий по частоте в секунду
- **`internal/usecase/ingest`** — очередь, обработчик событий, исходы (принято / отброшено)
- **`internal/usecase/top`** — чтение снимка по limit
- **`internal/usecase/stoplist`** — добавление и удаление слов через API
- **`internal/transport/nats`** — JetStream, постановка в очередь, подтверждение
- **`internal/transport/http`** — REST, метрики, pprof
- **`internal/infrastructure/cache`** — хранение снимков
- **`internal/infrastructure/metrics`** — Prometheus
- **`internal/infrastructure/config`** — переменные окружения

Зависимости идут внутрь: транспорт → сценарии использования → домен. Домен можно тестировать без NATS и HTTP.

---

## Одна горутина-писатель

Подписчик NATS:

1. читает пачку сообщений;
2. разбирает JSON в структуру события;
3. кладёт в очередь (если очередь полна — ждёт);
4. **не** обновляет окно сам.

Писатель в цикле:

- забирает событие из очереди и вызывает `ProcessAt`;
- раз в секунду по таймеру — `Tick` (сдвиг окна, сброс антифрода, новые снимки).

**Зачем:** общая `map` под мьютексом на горячем пути дала бы гонки и непредсказуемые задержки. Один писатель — проще гарантировать корректное истечение окна и общего счётчика.

**Минус:** пропускная способность записи упирается в одну CPU-горутину. Для текущей задачи (тренды в памяти, один узел) это осознанный обмен.

---

## Скользящее окно

Код: `internal/domain/trending/window.go`.

- 300 бакетов по 1 секунде → 5 минут (`WINDOW_SECONDS`, по умолчанию 300);
- в бакете: `map[string]uint64` — нормализованный запрос → вес за эту секунду;
- **общий счётчик** по всему окну обновляется при добавлении и при «протухании» бакета.

При сдвиге времени старый бакет вычитается из общего счётчика, карта бакета очищается и переиспользуется.

Слишком старые события отклоняются (`ignored_stale`). Слишком «будущие» — с допуском `MAX_FUTURE_SKEW` (2 с по умолчанию).

---

## Общий счётчик и Top-N

Без общего счётчика каждый Top-N пришлось бы собирать из 300 бакетов.

Top-N строится **кучей минимумов** фиксированного размера (`topn.go`) — сложность порядка O(M log N), где M — число уникальных запросов, N — размер топа. При равных очках порядок фиксируется по строке запроса.

---

## Кэш снимков

Чтений API обычно **гораздо больше**, чем новых событий. Поэтому раз в секунду писатель считает Top-N для лимитов 5, 10, 25, 50, 100 (`SNAPSHOT_LIMITS`) и атомарно подменяет снимок.

HTTP только читает готовый результат — без пересчёта на запросе.

**Минус:** в ответе `generated_at` может отставать от «живого» окна примерно на секунду. Для дашборда трендов это нормально.

---

## Стоп-лист

`map[string]struct{}`, при изменении — новая копия и атомарная подмена указателя. Проверка по токенам нормализованного запроса.

Стоп-лист **не вычищает** уже накопленные в окне очки — только новые события. Старый вклад уйдёт сам через 5 минут.

---

## Нормализация

Приведение к нижнему регистру, пробелы, пунктуация, выкидывание слов вроде «купить», «заказать», «новый», «дешево».

Пример: `"Купить   Айфон-17!!!"` → `"айфон 17"`.

Без тяжёлого NLP — дёшево на горячем пути, иногда склеивает разные формулировки ошибочно.

---

## Антифрод (упрощённый)

В текущей секунде считаем повторы одного запроса. После порога (`ANTIFRAUD_THRESHOLD_PER_SECOND`, по умолчанию 20) вес падает с **10** до **1**. Полного отбрасывания нет — резкий реальный всплеск не исчезает из статистики.

Счётчики секунды сбрасываются на каждом `Tick`.

---

## Ограничение памяти

`MAX_UNIQUE_QUERIES` (по умолчанию 200 000): новый редкий запрос может быть отклонён (`ignored_capacity`), если лимит уникальных ключей в окне уже достигнут. Уже популярные запросы продолжают обновляться.

Защита от бесконечной кардинальности строк и OOM.

---

## Контракт событий NATS

Тема по умолчанию: `search.events`. Тело:

```json
{
  "request_id": "8f4d6c4d-0d12-4d55-9f9d-1f1d6f8b7a11",
  "query": "купить айфон 17",
  "timestamp": "2026-05-24T12:00:01Z"
}
```

- **request_id** — для логов и разбора потерь;
- **query** — сырой текст, дальше нормализация и стоп-лист;
- **timestamp** — время на стороне отправителя, попадает в нужный секундный бакет.

Поток `search-events`, durable-консьюмер `search-trends`. Подтверждение в NATS — **после** успешной обработки писателем, только для принятых событий.

---

## Корректная остановка

1. сигнал → останов HTTP;
2. отмена контекста у подписчика NATS;
3. закрытие входа очереди;
4. ожидание писателя — дочитать очередь и финальный тик.

Так меньше шансов потерять уже принятые в очередь события.

---

## Почему без базы данных

Данные живут 5 минут, всё в памяти. БД добавила бы задержку и операционку без выигрыша для «тренды прямо сейчас».

---

## Почему NATS JetStream

Удобно поднять локально, есть persistence для разработки, один потребитель — не нужна тяжёлая платформа вроде Kafka.

---

## Почему chi

Тонкая обёртка над `net/http`, без лишнего фреймворка — middleware для request id, panic, pprof.

---

## Задачи и решения

1. **Рост памяти** → лимит уникальных запросов. Минус: редкие запросы теряются.
2. **Много чтений** → кэш снимков. Минус: отставание ~1 с.
3. **Гонки за окном** → один писатель. Минус: узкое место в одной горутине.
4. **Стоп-лист** → копия при записи, только новые события. Минус: старые очки до 5 минут.
5. **Разные формулировки** → лёгкая нормализация. Минус: возможны ложные склейки.
6. **Накрутка** → снижение веса. Минус: защита не идеальна.

---

## Масштабирование на будущее

Сейчас один узел. Дальше — шардирование по хэшу нормализованного запроса, несколько инстансов со своим окном и писателем, сверху — слияние локальных Top-N. Модель «в памяти + один писатель» сохраняется на шард.
